# Mode 06 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the app's existing, never-working mode 06 screen actually show on-board monitor test results, with honest naming and limits.

**Architecture:** Extract mode 06 out of `monitors.ts` into `src/lib/obd/mode06/`, matching `dtc/` and `uds/`. Keep every decision — what to ask, what a reply means, what a monitor is called — in pure functions; the walk in `features/monitors/lib/` only executes steps and hands replies to parsers. UI reads the result and does no reasoning.

**Tech Stack:** TypeScript strict, React Native / Expo Router, no test framework — assertions live in `scripts/selfcheck.ts`, run with `npx tsx`.

## Global Constraints

- **No brand-specific tables.** MIDs `0xE0`–`0xFF` and TIDs `0x80+` are manufacturer territory: report them, never name them.
- **Nothing that decides what to send or what a reply means touches the transport.** Pure functions take plain data.
- **A derived name must never read as certain.** Every test carries provenance, like `DtcConfidence` does for codes.
- **CAN only.** Non-CAN mode 06 is a different format needing per-brand init; out of scope.
- **Path alias:** `@/*` → `src/*`.
- **Commit style:** imperative subject describing the behaviour change, no `Co-Authored-By` trailer.
- **Checks:** `npm run typecheck` and `npm run check` must both pass before every commit.

```ts
export type MonitorFamily =
  | 'o2'
  | 'o2-heater'
  | 'catalyst'
  | 'evap'
  | 'egr'
  | 'misfire'
  | 'manufacturer'
  | 'other';

/** Mirrors CONFIDENCE_LABELS in dtc/types.ts: a name says how it was arrived at. */
export const MONITOR_CONFIDENCE_LABELS: Record<MonitorConfidence, string> = {
  named: 'Standard test',
  derived: 'Read from the monitor number',
  manufacturer: 'Manufacturer-defined',
  unlisted: 'Unlisted monitor',
};

export const FAMILY_LABELS: Record<MonitorFamily, string> = {
  o2: 'Oxygen sensors',
  'o2-heater': 'Oxygen sensor heaters',
  catalyst: 'Catalyst',
  evap: 'Evaporative system',
  egr: 'EGR and purge',
  misfire: 'Misfire',
  manufacturer: 'Manufacturer-defined',
  other: 'Other',
};

/** Failures first is handled by the screen; this is the resting order. */
export const FAMILY_ORDER: MonitorFamily[] = [
  'misfire',
  'catalyst',
  'o2',
  'o2-heater',
  'evap',
  'egr',
  'other',
  'manufacturer',
];

const NAMES: Record<number, string> = {
  /* the 29 entries moved from OBDMID_NAMES in parse.ts, unchanged */
};

/** Bank and sensor from a zero-based index into a four-sensors-per-bank range. */
function bankAndSensor(index: number): string {
  return `bank ${Math.floor(index / 4) + 1} sensor ${(index % 4) + 1}`;
}

/**
 * What a monitor id means, and how confident that is.
 *
 * The table comes first. Past it, several ranges in J1979 are laid out so
 * regularly that position is arithmetic rather than a lookup -- O2 sensors and
 * their heaters run four to a bank, misfire runs one per cylinder from 0xA1.
 * Those are derived and say so. 0xE0 and up is manufacturer territory and gets
 * no name at all: naming it would mean shipping somebody's reverse-engineered
 * list, which is the one thing this app refuses to do.
 */
export function describeMonitor(mid: number): {
  name: string;
  confidence: MonitorConfidence;
  family: MonitorFamily;
} {
  const hex = mid.toString(16).toUpperCase().padStart(2, '0');
  const family = familyFor(mid);

  const listed = NAMES[mid];
  if (listed) return { name: listed, confidence: 'named', family };

  if (mid >= 0xe0) {
    return { name: `Manufacturer test 0x${hex}`, confidence: 'manufacturer', family };
  }

  if (mid >= 0x01 && mid <= 0x20) {
    return { name: `O2 sensor ${bankAndSensor(mid - 0x01)}`, confidence: 'derived', family };
  }
  if (mid >= 0x21 && mid <= 0x2f) {
    return { name: `Catalyst bank ${mid - 0x20}`, confidence: 'derived', family };
  }
  if (mid >= 0x41 && mid <= 0x50) {
    return { name: `O2 heater ${bankAndSensor(mid - 0x41)}`, confidence: 'derived', family };
  }
  if (mid >= 0xa1 && mid <= 0xac) {
    return { name: `Misfire cylinder ${mid - 0xa0}`, confidence: 'derived', family };
  }

  return { name: `Monitor 0x${hex}`, confidence: 'unlisted', family };
}

function familyFor(mid: number): MonitorFamily {
  if (mid >= 0xe0) return 'manufacturer';
  if (mid === 0x81 || (mid >= 0xa1 && mid <= 0xac)) return 'misfire';
  if (mid >= 0x01 && mid <= 0x20) return 'o2';
  if (mid >= 0x21 && mid <= 0x2f) return 'catalyst';
  if (mid >= 0x39 && mid <= 0x3d) return 'evap';
  if (mid >= 0x31 && mid <= 0x38) return 'egr';
  if (mid >= 0x41 && mid <= 0x50) return 'o2-heater';
  return 'other';
}
```

```ts
/**
 * What a test id is called.
 *
 * J1979 defines test ids per monitor family, and the same number means
 * different things under different monitors -- so naming them from the id
 * alone would be wrong more often than right. Only the split that is certain
 * is stated: 0x80 and up is manufacturer-defined. Everything else is shown as
 * its number, which is still enough to tell two tests under one monitor apart.
 */
export function describeTest(tid: number): { name: string; manufacturerDefined: boolean } {
  const hex = tid.toString(16).toUpperCase().padStart(2, '0');
  const manufacturerDefined = tid >= 0x80;
  return {
    name: manufacturerDefined ? `Manufacturer test 0x${hex}` : `Test 0x${hex}`,
    manufacturerDefined,
  };
}
```

```ts
import { extractPayload } from '../protocol';
import { chainsToNextBlock, decodeSupportMask } from '../supported';

/**
 * Support blocks for mode 06.
 *
 * Deliberately not SUPPORT_BLOCK_PIDS. Monitor ids run to 0xFF and so need the
 * E0 block; mode 01 PIDs do not, and that constant has assertions of its own
 * riding on its length.
 */
export const MODE06_SUPPORT_BLOCKS = ['00', '20', '40', '60', '80', 'A0', 'C0', 'E0'] as const;

export function supportRequest(block: string): string {
  return `06${block}`;
}

export function testRequest(mid: string): string {
  return `06${mid}`;
}

/** Expands one support block's reply into the monitor ids it advertises. */
export function parseSupportedMids(hex: string, block: string): string[] {
  const payload = extractPayload(hex, '46', block);
  if (!payload || payload.length < 4) return [];
  return decodeSupportMask(block, payload.slice(0, 4));
}

/** Whether the block just read says the following one exists. */
export function chainsOnward(block: string, supported: string[]): boolean {
  return chainsToNextBlock(block, supported);
}
```

- [ ] **Step 4: Implement `run-mode06.ts`**

```ts
import type { ObdResponse } from '@/lib/obd/protocol';
import { indicatesControllerFault } from '@/lib/obd/protocol';
import {
  MODE06_SUPPORT_BLOCKS,
  chainsOnward,
  parseMonitorTests,
  parseSupportedMids,
  supportRequest,
  testRequest,
  type MonitorTest,
} from '@/lib/obd/mode06';

const SUPPORT_TIMEOUT_MS = 4000;
const TEST_TIMEOUT_MS = 5000;

export type Mode06Client = {
  query(command: string, timeoutMs?: number): Promise<ObdResponse>;
};

export type Mode06Result = {
  tests: MonitorTest[];
  /** How many monitor ids the car said it had. */
  advertised: number;
  /** Advertised, asked, and did not answer. Reported rather than hidden. */
  silent: number;
  /** True when the adapter dropped off the bus and the walk was called off. */
  aborted: boolean;
};

/**
 * Reads every on-board test the car advertises.
 *
 * The support mask is walked first -- asking for a monitor the car never
 * claimed wastes a round trip and reads as silence when it comes back empty.
 * A monitor that refuses individually is counted and skipped, because one
 * unsupported test is not a reason to abandon the other twenty. An adapter
 * fault is different: a controller that has dropped off the bus answers every
 * remaining request with the same error, so the walk stops rather than
 * spending twenty timeouts proving it.
 */
export async function runMode06(
  client: Mode06Client,
  onProgress?: (done: number, total: number) => void,
): Promise<Mode06Result> {
  const mids: string[] = [];

  for (const block of MODE06_SUPPORT_BLOCKS) {
    let reply: ObdResponse;
    try {
      reply = await client.query(supportRequest(block), SUPPORT_TIMEOUT_MS);
    } catch {
      break;
    }

    if (!reply.ok) {
      if (indicatesControllerFault(reply.reason)) {
        return { tests: [], advertised: mids.length, silent: 0, aborted: true };
      }
      break;
    }

    const found = parseSupportedMids(reply.hex, block);
    // A support block lists the next block as one of its own ids; it is a
    // chain marker, not a monitor, so it must not be asked for.
    const blocks = new Set<string>(MODE06_SUPPORT_BLOCKS);
    mids.push(...found.filter((mid) => !blocks.has(mid)));

    if (!chainsOnward(block, found)) break;
  }

  const tests: MonitorTest[] = [];
  let silent = 0;

  for (const [index, mid] of mids.entries()) {
    onProgress?.(index, mids.length);

    let reply: ObdResponse;
    try {
      reply = await client.query(testRequest(mid), TEST_TIMEOUT_MS);
    } catch {
      silent += 1;
      continue;
    }

    if (!reply.ok) {
      if (indicatesControllerFault(reply.reason)) {
        return { tests, advertised: mids.length, silent, aborted: true };
      }
      silent += 1;
      continue;
    }

    tests.push(...parseMonitorTests(reply.hex));
  }

  onProgress?.(mids.length, mids.length);
  return { tests, advertised: mids.length, silent, aborted: false };
}
```

## Known limitation, deliberately not fixed here

The `SCALING` table reads every value as unsigned 16-bit. Several J1979 scaling
ids are signed two's complement, which would make those tests report large
positive numbers where they should report small negative ones. The spec called
for adding signed handling; it is **not** in this plan, because the signedness
of specific ids could not be verified against the standard from the code alone,
and guessing which ids are signed would put a confident-looking meter next to a
wrong number — the exact failure this app is built to avoid.

The table's existing comment already says only confidently-stated entries are
listed, and anything unrecognised falls through to raw counts. That behaviour is
preserved. Auditing the table against a copy of J1979 is a follow-up, and should
land with assertions per id.
