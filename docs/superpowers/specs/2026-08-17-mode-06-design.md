# Mode 06 — on-board monitoring test results

**Status:** design approved, not yet implemented
**Date:** 2026-08-17

## The problem

Mode 06 is already in the app and has never once produced a result.

`parseMonitorTests` in `src/lib/obd/monitors.ts` decodes the nine-byte test
records correctly. `MonitorsScreen` already renders them under "On-board test
results". The break is in what the screen asks for:

```ts
const results = await client.query('0600', 6000);
if (results.ok) setTests(parseMonitorTests(results.hex));
```

MID `00` is not a test. It is the support bitmask — the same chained-block
scheme as mode 01 PID `00`, which `src/lib/obd/supported.ts` already implements.
A car answers `46 00 BF FF C0 00`: five payload bytes saying which MIDs it
supports. `parseMonitorTests` walks nine-byte records, five bytes never
satisfies `i + 8 < payload.length`, and it returns `[]`.

So on every car, on every read, the section renders "No test results reported
yet." The failure has no shape: it looks exactly like a car with nothing to say.

Nothing in `scripts/selfcheck.ts` references `parseMonitorTests`. It is the only
parser in the protocol layer with no assertions over it, which is why this
shipped and stayed shipped.

**The work is the request side and the test coverage, not the decoder.**

## Layout

`monitors.ts` currently holds two unrelated protocols — readiness (mode 01 PID
`01`) and mode 06. The mode 06 half roughly triples under this design, so it
moves out:

```
src/lib/obd/mode06/
  index.ts          re-exports
  plan.ts           what to ask: support blocks, MID requests
  parse.ts          the nine-byte record decoder and its scaling table
  monitor-ids.ts    MID names, derivation by range, family assignment
  test-ids.ts       TID names, conservative
```

This matches how `dtc/` and `uds/` are already laid out. `monitors.ts` is left
as readiness alone.

## The request side

Pure plan, impure walk. Nothing that decides what to send touches the transport.

`plan.ts` exposes:

- `MODE06_SUPPORT_BLOCKS = ['00','20','40','60','80','A0','C0','E0']` — its own
  list, not `SUPPORT_BLOCK_PIDS`. Mode 06 MIDs run to `0xFF` and need the `E0`
  block; mode 01 does not, and that constant has selfcheck assertions over it.
- `supportRequest(block)` → `06<block>`
- `testRequest(mid)` → `06<mid>`
- `parseSupportedMids(hex, block)` → `extractPayload(hex, '46', block)`, then the
  existing `decodeSupportMask` over the first four bytes
- chaining reuses `chainsToNextBlock` unchanged

`src/features/monitors/lib/run-mode06.ts` walks it, mirroring
`features/scan/lib/run-scan.ts`:

1. Query support blocks while the chain bit is set.
2. Query each advertised MID in turn.
3. A MID that refuses or times out is skipped and counted, not swallowed — the
   screen can then say how many tests the car advertised but did not answer.
4. `indicatesControllerFault` aborts the whole walk. An adapter that has dropped
   off the bus answers every remaining request with the same error, so carrying
   on tests nothing and ends by blaming the car.

Cost is one round trip per supported MID, typically ten to twenty-five, so two
to four seconds. The existing `Button busy` gains a count — "Reading 7 of 19".

## Naming and provenance

Three tiers, mirroring `resolveDtcDetail`, so a derived name never reads as
gospel.

1. **Named.** The existing 29-entry table.
2. **Derived by range**, where the standard makes the position arithmetic:
   - `0x01–0x10` — O2 sensor, bank `⌊(mid-1)/4⌋+1`, sensor `((mid-1)%4)+1`
   - `0x21–0x2F` — catalyst, bank `mid-0x20`
   - `0x41–0x50` — O2 heater, same arithmetic as the sensors
   - `0xA1–0xAC` — misfire, cylinder `mid-0xA0`
3. **Manufacturer-defined.** `0xE0–0xFF` is manufacturer territory. It never
   gets a derived name, and says so rather than showing a bare number.

Anything else is `unlisted`: shown with its number and its values, described as
a monitor this app does not have a name for.

Each test carries `confidence: 'named' | 'derived' | 'manufacturer' | 'unlisted'`
with labels, the way `CONFIDENCE_LABELS` works for codes.

`test-ids.ts` does the same for TIDs, conservatively — `0x80+` is
manufacturer-defined, and only TIDs that can be stated confidently are named.
The TID renders as a second line. Without it, the three test IDs that
per-cylinder misfire returns render as three identical rows labelled "Misfire
cylinder 1" with three different numbers and no way to tell them apart.

## The verdict

`passed: value >= min && value <= max` is too blunt in three ways.

**Limits may be one-sided.** A record carrying only an upper limit reports `min`
as `0x0000`, only a lower reports `max` as `0xFFFF`. The parse result gains
`limit: 'both' | 'upper' | 'lower' | 'none'`, and the caption reads "must stay
below 0.72" rather than inventing the range "allowed 0.00–0.72".

**Some scaling IDs are signed.** The table currently reads every value as
unsigned 16-bit. Signed two's-complement handling is added *only* for entries
that can be verified against J1979; anything not verifiable stays out of the
table entirely and falls through to raw counts, which is the stance the existing
comment already takes. **This table needs auditing against the standard during
implementation — it is the one part of this design written from memory rather
than from the code.**

**Margin is the whole point.** A test that passes at 96% of its limit is the
finding; a bare "Pass" throws it away. Each row gets a `Meter` showing where the
value sits between its limits.

## Presentation

Collapsible groups by family — O2 sensors, O2 heaters, catalyst, EVAP, EGR,
misfire, manufacturer, other — collapsed by default, each header carrying its
count and whether anything inside failed. Any failing test also surfaces above
the groups, so a failure cannot hide inside a collapsed section.

Family is computed from the MID range in `monitor-ids.ts`. The screen does no
reasoning of its own, consistent with the rest of the app.

## Tests

New assertions in `scripts/selfcheck.ts`, which currently has none for any of
this:

- support mask expansion for mode 06 blocks, and chaining through to `E0`
- multi-record slicing; trailing bytes that do not complete a record; the
  `monitorId === 0` skip
- every scaling table entry, including the temperature offset and each signed
  case
- all four limit modes
- each derivation range, at both ends: `0x0A` is O2 bank 3 sensor 2, `0xA4` is
  misfire cylinder 4, `0xE1` is manufacturer-defined with no derived name
- family assignment for each range
- **the regression that started this**: `4600BFFFC000` parses as a support mask,
  and a support-mask reply never reaches the record parser

## Out of scope

- **Non-CAN mode 06.** A different legacy format needing per-brand
  initialisation — the same reason the module scan is CAN-only.
- **Invented names for manufacturer TIDs.** No brand tables here.
- **Readiness decoding.** Untouched.
